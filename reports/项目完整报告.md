# Decompose Agent 项目完整报告

- 报告日期：2026-11-16
- 项目名称：Decompose Agent
- 项目类型：复杂经营分析型 Agent 原型
- 技术栈：Python、LangGraph、LangChain、OpenAI 兼容模型接口、FastAPI、Pydantic、asyncio
- 当前状态：主链可运行，模拟数据闭环完成，自动化测试通过；真实数据源和生产部署尚未接入

## 1. 项目概述

Decompose Agent 是一个面向经营分析问题的 Agent 原型。

它解决的问题不是“查一条订单”或“执行一个有依赖的多步操作”，而是把跨指标、跨产品线的复杂问题拆成若干可以独立执行的数据查询，再综合为一份分析报告。

典型问题：

- 对比三条产品线的退款率和投诉趋势。
- 哪些产品线的投诉增长最快。
- 某产品在某月份的销售、退款和投诉情况如何。
- 三次退款分别发生在哪个月，主要原因是什么。

项目的核心思想是：

```text
先规划 → 再并行检索 → 最后综合
```

它主动限制模型的自由循环，避免 ReAct Agent 在多轮工具调用中产生不可预测的轮数、延迟和上下文增长。

## 2. 项目目标与非目标

### 目标

1. 验证“拆解—并行检索—综合”是否适合跨维度分析。
2. 让每个子任务都对应明确的工具和参数。
3. 让单个工具或单个子任务失败时仍可保留部分结果。
4. 控制进入综合 Prompt 的上下文长度。
5. 提供 CLI 和 FastAPI 两种调用方式。
6. 提供最小但可扩展的记忆、会话和安全基础。

### 非目标

1. 当前不连接真实企业数据库。
2. 当前不实现生产级权限和租户隔离。
3. 当前不处理任意 SQL 查询。
4. 当前不保证三个产品线拥有完整相同月份的数据。
5. 当前不把 PostgreSQL/pgvector 路径声明为生产验证完成。

## 3. 系统架构

```text
Client / CLI
     ↓
FastAPI / run_query
     ↓
LangGraph StateGraph
     ↓
   classify
   recall
    ↓ 两路汇合
  decompose
    ↓
结构化检索计划
    ↓
 validate plan
    ↓
 asyncio.gather
   ├─ sales
   ├─ refunds
   ├─ complaints
   └─ products
    ↓
 synthesize
    ↓
   write
    ↓
 response
```

### 3.1 `classify`

- 在已注册业务域中选择一个域。
- 存在业务域时会调用 LLM。
- LLM 失败或返回未知域时，用 trigger 关键词做确定性兜底。
- 当前分类结果记录在 state 中，但主检索节点仍使用全局读工具目录。

### 3.2 `recall`

- 根据 `user_id` 召回结构化偏好和观察。
- 默认使用 `InMemoryStore`。
- 当前综合节点只把偏好注入 Prompt，观察字段尚未实际使用。

### 3.3 `decompose`

- 调用一次核心 LLM。
- 输入包含用户原问题和可用工具目录。
- 输出限制为最多 5 个结构化步骤。
- 每个步骤包含 `question`、`tool` 和 `arguments`。
- 工具名与参数经过代码校验。
- 无法生成合法计划时，所有读工具各执行一次全量查询。

### 3.4 `retrieve`

- 使用 `asyncio.gather` 并行执行各计划步骤。
- 每一步只调用计划指定的工具。
- 工具结果是文本时直接使用，其他类型转为 JSON 文本。
- 每个结果最多保留 2,000 字符。
- 单个步骤异常使用 `status=error` 返回，其他步骤继续执行。

### 3.5 `synthesize`

- 调用一次核心 LLM。
- 拼接原始问题、每个步骤的问题、工具、参数、状态和结果。
- 每个结果再次截断到 500 字符。
- 注入用户偏好。
- 清理输出后追加一条 `AIMessage`。

### 3.6 `write`

- 默认使用确定性昵称抽取。
- 不额外调用 LLM。
- 可通过配置启用 LLM 富偏好抽取。

## 4. 数据与工具

当前 analytics 域包含三条产品线和经营数据的模拟工具。

### 工具

| 工具 | 输入 | 输出 |
|---|---|---|
| `search_sales` | `product_id`、`month` | 订单量、收入、合计和逐月明细 |
| `search_refunds` | `product_id`、`month` | 退款笔数、金额、原因分布 |
| `search_complaints` | `product_id`、`month`、`category` | 投诉数量、严重度和类别分布 |
| `list_products` | 无 | 产品线名称、类别、价格、上线月份 |

### 产品线

| ID | 名称 | 销售数据范围 |
|---|---|---|
| `prod_a` | AI客服Agent | 2025-03 至 2025-08 |
| `prod_b` | 数据分析平台 | 2025-01 至 2025-08 |
| `prod_c` | 知识库SaaS | 2025-06 至 2025-08 |

数据共包含 17 条销售记录、13 条退款记录和 12 条投诉记录。由于各产品线上线时间不同，比较时应说明覆盖区间，不能把 `prod_c` 的三个月份误讲成八个月完整数据。

## 5. 结构化计划设计

### 为什么要结构化

如果拆解只输出自然语言句子，检索节点无法知道：

- 应该使用哪个工具。
- 产品 ID 是什么。
- 月份是什么。
- 投诉类别是什么。

旧实现把整句话传给工具，导致工具虽然成功执行，却没有检索到业务数据。

现在的计划示例：

```json
{
  "steps": [
    {
      "question": "查询三条产品线的退款数据",
      "tool": "search_refunds",
      "arguments": {}
    },
    {
      "question": "查询三条产品线的销售数据",
      "tool": "search_sales",
      "arguments": {}
    }
  ]
}
```

### 校验点

1. 顶层必须是对象且包含 `steps` 数组。
2. 每步必须包含非空 `question` 和非空 `tool`。
3. 工具必须是当前工具的精确名称。
4. `arguments` 使用工具的 Pydantic schema 校验。
5. 最多执行 5 步。
6. 相同工具和相同参数只执行一次。
7. 非法步骤被删除；全部非法时进入全量兜底。

### 权衡

优点：

- 参数语义明确。
- 工具调用可控。
- 便于审计和测试。
- 可以逐步加入权限过滤和工具白名单。

代价：

- 对模型的结构化输出能力提出要求。
- JSON 解析或参数错误需要兜底逻辑。
- 计划质量会直接影响报告质量。

## 6. 会话与记忆

项目有两套不同作用域的数据。

### 会话状态

由 LangGraph checkpointer 管理。

- 主键：`thread_id`
- 内容：该会话的完整图状态和消息
- 默认：`MemorySaver`
- 可选：PostgreSQL checkpointer
- 默认生命周期：进程内存，重启即丢

### 长期偏好

由 `MemoryStore` 管理。

- 主键：`user_id`
- 内容：偏好 KV 和观察文本
- 默认：`InMemoryStore`
- 偏好策略：latest-wins
- 可选：PostgreSQL + pgvector 参考实现

pgvector 实现包含联合主键和 UPSERT，但没有真实 PostgreSQL 环境的自动化集成验证。

### 会话索引

`SessionStore` 维护“用户拥有哪些 thread”的轻量列表，用于会话列表接口。

- 默认 `InMemorySessionStore`
- 与完整对话状态分开存储

## 7. 服务接口

### FastAPI

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/health` | 健康检查 |
| POST | `/agent/chat` | 同步对话 |
| POST | `/agent/chat/stream` | 逐节点 SSE 更新，最后发送完整 reply |
| GET | `/agent/sessions` | 列出用户会话 |
| GET | `/agent/sessions/{thread_id}/messages` | 读取会话消息 |
| DELETE | `/agent/sessions/{thread_id}` | 删除会话索引 |

### CLI

```bash
decompose "对比三个产品线的退款率和投诉趋势"
```

或：

```bash
python -m agent_starter.cli "对比三个产品线的退款率和投诉趋势"
```

CLI 的交互循环会为每次输入调用 `build_graph()`，因此默认不依赖长期会话状态；长期偏好存储仍可跨调用存在。

## 8. 安全与上下文控制

当前主图只执行读工具，不执行写业务工具。

安全控制包括：

1. 工具名只能来自当前工具映射。
2. 工具参数经过 Pydantic schema 校验。
3. 最大计划步骤数限制。
4. 工具结果最大 2,000 字符。
5. 综合输入每条结果最大 500 字符。
6. 最终输出经过 `sanitize_output`。
7. 失败工具保留明确状态，不伪装为成功数据。

项目还保留旧模板中的权限、输入防注入和 skill 能力，但当前 Decompose 主链没有完整接入这些能力。

## 13. 已知限制

1. `classify` 尚未控制可选工具集合。
2. 兜底计划会调用全部读工具，可能产生宽泛分析。
3. 三条产品线数据时间范围不一致。
4. 观察记忆已召回但尚未注入综合 Prompt。
5. SSE 是节点事件，不是 token 流。
6. PostgreSQL checkpointer 和 pgvector 路径未在 CI 中验证。
7. 没有真实模型评测集、准确率或延迟数据。
8. 仓库保留旧 ReAct 模块，阅读时需要以 `main.py` 和 `graph.py` 为准。

## 15. 面试版项目介绍

> 这是一个面向多产品线经营分析的 LangGraph Agent。普通 ReAct 适合有依赖的串行操作，但对比不同产品线的销售、退款和投诉时，子任务可以独立执行。因此我把流程设计为拆解、并行检索和统一综合。拆解节点让模型生成结构化计划，每一步包含问题、工具和参数，代码会校验工具白名单和 Pydantic 参数。检索节点用 asyncio.gather 并行执行，单个工具失败只影响该步骤。每条结果先截断到 2,000 字符，送入综合节点前再截断到 500 字符。当前使用模拟数据，默认内存会话，PostgreSQL/pgvector 作为可选参考实现。

## 16. 总结

这个项目的核心价值不在于“调用了多少模型”，而在于把不可控的工具循环改造成有边界、可校验、可并行、可部分失败的检索计划执行流程。

当前版本适合作为 Agent 编排、结构化工具调用、上下文控制和失败隔离的学习与面试项目。要成为真实生产系统，下一步最需要补充的是真实数据、评测指标、可观测性和鉴权，而不是继续增加界面或工具数量。
